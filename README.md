# mic_array: 3-microphone sound direction finder (Raspberry Pi Pico 2)

Three I2S MEMS microphones sampled in lockstep by a Raspberry Pi Pico 2, bare metal, no RTOS. The firmware measures **how many samples later each microphone hears a sound** (TDOA, time difference of arrival) and turns those delays into an **azimuth angle** toward the source.

> **Purpose of the project:** a sound-direction sensor for a **UGV (unmanned ground vehicle)**, so the robot can tell which way a sound came from.
> **The servo in this repository is only a test rig.** It is a quick, visible way to check that the angle is right (a pointer that swings toward a clap). It is not part of the final design. In the UGV the azimuth value would go to the drive/navigation code instead.

## How it works

```
3 mics --I2S--> PIO --> RX FIFO --DMA--> ring buffer (RAM) --> main loop
```

- **One clock for all mics.** A PIO program generates BCLK (GPIO20) and WS (GPIO21) and samples **four consecutive GPIOs on every BCLK tick**. Each mic has its own data wire, so each 4-bit group contains one bit per mic. All three mics are therefore sampled at the same instant, which is what makes sub-millisecond delay measurement possible.
- **DMA ring buffer.** DMA copies every word into a 32 KB ring without stopping, so the mic clock never stalls while the CPU is busy.
- **Sample rate** is about 48 kHz (150 MHz / 24.4 / 2 / 64), 24-bit samples. One sample is 20.8 µs, which is about 7.15 mm of sound travel.

The main loop works on a window of the newest 512 frames (10.7 ms):

1. **Snapshot**: copy and decode the newest 512 frames out of the ring.
2. **Gate**: if any mic's peak-to-peak level is below `TDOA_GATE`, skip the window (a quiet room would only correlate noise).
3. **Center**: subtract each mic's mean to remove the DC offset (about -360000 counts).
4. **Correlate**: for each pair (1-2, 1-3, 2-3) try every shift from `-MAX_SHIFT` to `+MAX_SHIFT` and keep the one with the best cross-correlation score.
5. **Confidence**: the score is divided by `sqrt(energy_a * energy_b)`, giving -1..+1 per pair. Below `MIN_CONF` the mics did not hear the same sound, so the window is ignored.
6. **Direction**: the three delays are combined by least squares (far-field plane-wave model) into a direction vector, then an azimuth. A consistency check (`k13` should equal `k12 + k23`) rejects windows where one pair locked onto the wrong peak. The last few angles are median-filtered.
7. **Servo (test rig)**: the servo steps toward the angle, at most 15° per update.

### Delay convention

`k > 0` means the **second** mic of the pair hears the sound `k` samples **later**.
`check = k13 - (k12 + k23)` must be about 0, because delay(1→3) = delay(1→2) + delay(2→3).

### Sample format

Each mic's raw 32-bit word has the I2S delay bit on top, so it is decoded as `((int32_t)(w << 1)) >> 8`: a signed 24-bit value (full scale ±8388608).

## The PCB

The board lives in [`electrical/`](electrical) (KiCad). It is deliberately simple, and it was made for two reasons:

1. **Learning.** Even a small board is a complete exercise: schematic, footprints, placement, routing, DRC, and getting it manufactured.
2. **Reuse the parts as they are.** The microphones are ready-made breakout boards, already soldered to their pins, and the breakouts carry their own resistors and supporting parts. So the carrier PCB only needs **three 100 nF decoupling capacitors and pin sockets**: the mics plug into sockets and the Pico 2 plugs into sockets. Nothing is soldered that you might want to swap or reuse later.

Board facts:

- Three 1x06 mic sockets (`MIC_1`, `MIC_2`, `MIC_3`), three 100 nF 0805 capacitors (`C1` to `C3`) between 3V3 and GND, one Pico 2 on sockets.
- The mic positions are fixed by the board, because it is a microphone array. This is what defines the baselines used by the direction solver (see [Tuning](#tuning)).
- Board size is about 107.5 x 68.5 mm (Edge.Cuts rectangle).
- Fully routed, DRC clean.
- The mic breakouts plug into the headers horizontally.

### Mic header pinout (all three headers identical)

| Header pin | Signal | Goes to |
|---|---|---|
| 1 | 3V3 | Pico 3V3 (pin 36) |
| 2 | GND | GND |
| 3 | BCLK | shared, Pico GPIO20 |
| 4 | DOUT | **individual**, one Pico GPIO per mic |
| 5 | WS (LRCLK) | shared, Pico GPIO21 |
| 6 | SEL | GND, so every mic talks in the **left** slot only |

Check the silkscreen of your breakouts against this order before plugging them in. The schematic labels the WS net "Data"; it is the word-select line.

## Pin mapping

| Signal | Pico 2 physical pin | GPIO |
|---|---|---|
| BCLK (shared) | 26 | GPIO20 |
| WS (shared) | 27 | GPIO21 |
| Mic 1 DOUT | 9 | GPIO6 |
| Mic 2 DOUT | 10 | GPIO7 |
| Mic 3 DOUT | 11 | GPIO8 |
| 3V3 | 36 | |
| GND | 8 | |
| Servo signal (test rig, not on the PCB) | 21 | GPIO16 |

> **Check before flashing:** the data pins in the firmware must match how the mics are wired. The PIO samples a window of 4 consecutive GPIOs starting at `DATA_BASE`, and `mic_pin[]` in `src/parse.c` lists which GPIO belongs to which mic.
> - **This PCB:** `DATA_BASE = 6` and `mic_pin = { 6, 7, 8 }` (window GPIO6..9, GPIO9 unused).
> - **Original breadboard wiring:** `DATA_BASE = 7` and `mic_pin = { 9, 8, 7 }`.
>
> BCLK must stay on the pin directly below WS (WS = BCLK + 1), which it does here.

## Build and flash

Everything uses the [Raspberry Pi Pico SDK](https://github.com/raspberrypi/pico-sdk). The CMake project is called `sound` and builds for `pico2`; the output is `build/sound.uf2`. USB serial output is on, UART output is off.

### Linux (with the helper scripts)

**1. Install the tools**

| Distro | Command |
|---|---|
| Arch | `sudo pacman -S cmake arm-none-eabi-gcc arm-none-eabi-newlib picotool` |
| Debian/Ubuntu | `sudo apt install cmake gcc-arm-none-eabi libnewlib-arm-none-eabi build-essential picotool` |

Get the SDK and point `PICO_SDK_PATH` at it:

```bash
git clone https://github.com/raspberrypi/pico-sdk.git ~/pico-sdk
cd ~/pico-sdk && git submodule update --init
echo 'export PICO_SDK_PATH=$HOME/pico-sdk' >> ~/.bashrc   # then open a new shell
```

If your distro does not package `picotool`, build it from <https://github.com/raspberrypi/picotool>.

**2. Configure once**

```bash
mkdir -p build
cd build && cmake .. && cd ..
```

**3. Build with `make.sh`**

```bash
./make.sh
```

The script changes into `build/`, runs `make -j`, and returns. It expects `build/` to exist and to have been configured (step 2). After you move or rename source files, delete `build/` and redo step 2.

**4. Flash with `flash.sh`**

```bash
./flash.sh
```

This runs `picotool load -f build/sound.uf2`. The `-f` flag asks a board that is already running this firmware to reboot into the bootloader by itself. The very first time (or if that fails), put the board in BOOTSEL mode by hand: hold the BOOTSEL button while plugging in USB, then run the script again. You can also drag `build/sound.uf2` onto the `RP2350` drive that appears.

If `picotool` complains about permissions, install the picotool udev rules or run it with `sudo`.

**5. Read the output**

The Pico shows up as a USB serial device, usually `/dev/ttyACM0`.

```bash
screen /dev/ttyACM0 115200        # quit: Ctrl-A, then K
# or
minicom -D /dev/ttyACM0
```

You must be in the right group to open it: `dialout` on Debian/Ubuntu, `uucp` on Arch (`sudo usermod -aG uucp $USER`, then log out and in). Baud rate is ignored by USB CDC, any value works.

### Windows

**Option A: VS Code (easiest).** Install the **Raspberry Pi Pico** extension. It downloads the SDK, the ARM toolchain, CMake, Ninja and picotool for you. Use *Import Project* on this folder, choose board `pico2`, then *Compile* and *Run* (or copy `build/sound.uf2` yourself).

**Option B: command line.**

1. Install the [Arm GNU Toolchain](https://developer.arm.com/downloads/-/arm-gnu-toolchain-downloads) (`arm-none-eabi`), [CMake](https://cmake.org/download/), [Ninja](https://github.com/ninja-build/ninja/releases) and [Git](https://git-scm.com/).
2. Clone the Pico SDK with its submodules and set `PICO_SDK_PATH`:
   ```powershell
   git clone https://github.com/raspberrypi/pico-sdk.git C:\pico-sdk
   cd C:\pico-sdk; git submodule update --init
   setx PICO_SDK_PATH C:\pico-sdk
   ```
   Open a new terminal afterwards.
3. Build:
   ```powershell
   mkdir build
   cd build
   cmake -G Ninja ..
   ninja
   ```
4. Flash: hold **BOOTSEL** while plugging in the Pico, then copy `build\sound.uf2` onto the `RP2350` drive. Or use [picotool for Windows](https://github.com/raspberrypi/pico-sdk-tools/releases): `picotool load -f build\sound.uf2`.
5. Read the output: find the COM port in Device Manager (*Ports*), then open it in PuTTY, Tera Term, or the VS Code serial monitor.

**The helper scripts on Windows:** `make.sh` and `flash.sh` are bash scripts. They run from **Git Bash** as they are, as long as `make` is installed (the Ninja route above does not produce a Makefile, so use the commands in step 3 instead). Under **WSL** building works exactly like Linux, but WSL cannot see the USB board by default, so flash from Windows (step 4) or attach the device with [`usbipd-win`](https://github.com/dorssel/usbipd-win).

### macOS

```bash
brew install cmake picotool
brew install --cask gcc-arm-embedded
git clone https://github.com/raspberrypi/pico-sdk.git ~/pico-sdk
cd ~/pico-sdk && git submodule update --init
export PICO_SDK_PATH=~/pico-sdk
```

Then follow the Linux steps (the scripts work as they are). The serial device is `/dev/tty.usbmodem*`: `screen /dev/tty.usbmodem* 115200`.

## Testing

You need a quiet room and a sound that is loud and sharp enough: a **hand clap**, a **finger snap**, or a **1 kHz tone** from a phone.

**1. Power-up check.** Open the serial monitor and reset the board. You should see `|BOOT|`. While the room is quiet the firmware stays silent (windows below `TDOA_GATE` are skipped without printing).

**2. Make a sound.** Each accepted window prints one line:

```
k12=  5 (  104.2 us) | k13=-12 ( -250.0 us) | k23=-16 ( -333.3 us) | check=-1
  -> azimuth 34 deg
```

| Field | Meaning |
|---|---|
| `k12`, `k13`, `k23` | delay between that mic pair in samples (and in µs). Positive: the second mic hears it later. |
| `check` | `k13 - (k12 + k23)`. Should be 0 or ±1. Larger means one pair picked a wrong peak. |
| `azimuth` | direction in degrees from the front axis, positive toward +x. Only printed when the reading passed all checks. |

**3. Sanity tests, in this order:**

1. **Broadside test.** Clap straight in front of the board, equally far from all mics. The delays should be small.
2. **Left/right test.** Clap close to one mic. The pairs involving that mic should show it hearing the sound **first**; walk to the other side and the signs should flip. If the servo moves the wrong way, set `SERVO_REVERSE` to `1` in `servo.h`.
3. **Consistency.** Over several claps `check` should stay at 0 or ±1. If it is regularly larger, raise the loudness (closer or louder source) or check the wiring.
4. **Range.** The maximum possible delay is about `MIC_DISTANCE / speed of sound * 48000` samples, so delays near ±`MAX_SHIFT` mean the correlation hit its search limit and the reading is rejected.

**Servo test rig.** With the servo on GPIO16 (and its own power, common ground) the pointer should swing toward the clap, moving at most 15° per update. `calib_servo()` in `servo.c` does a slow sweep (90 → 0 → 180 → 90) to find the mechanical limits; narrow `SERVO_MIN_US`/`SERVO_MAX_US` in `servo.h` if the servo buzzes at an end. Servos draw current spikes, so power them from a supply that can handle it and not from the Pico's 3V3.

**If nothing is ever printed:** the gate is probably too high for your room or mic gain. Lower `TDOA_GATE` in `parse.h`. A quiet room should be about 10000 to 20000 counts peak-to-peak, and a 1 kHz tone about 35000 or more.

## Tuning

| Setting | File | Meaning |
|---|---|---|
| `TDOA_GATE` | `include/parse.h` | loudness threshold (peak-to-peak counts) for running the correlation |
| `MIN_CONF` | `include/parse.h` | minimum match quality per pair, -1..+1 (start at 0.5) |
| `SAMPLES` | `include/mic_tdoa.h` | window length in frames, 512 maximum with the 32 KB ring |
| `MIC_DISTANCE` | `include/mic_tdoa.h` | largest mic spacing in cm; sets `MAX_SHIFT` (25 at 17 cm) |
| `MIC_D12_CM`, `MIC_D13_CM`, `MIC_D23_CM` | `include/servo.h` | measured distances between mic pairs (centre of sound hole to centre of sound hole) |
| `MIC3_SIDE`, `SERVO_FRONT_OFFSET_DEG` | `include/servo.h` | which side mic 3 is on, and where "front" points |
| `DOA_NORM_MIN/MAX`, `DOA_MEDIAN_N` | `include/servo.h` | direction-vector quality limits and angle smoothing length |

The three `MIC_Dxx_CM` values must match the real board. Measure them on your PCB, they define the geometry of the direction solver.

## Status and known limits

- **Works:** synchronized 3-mic capture, TDOA between all pairs, confidence rejection, delay-to-azimuth, servo test rig.
- **In progress:** sub-sample (fractional) delay estimation, which needs the delays and the servo interface to move from `int` to `float`.
- **Resolution** is one sample (20.8 µs, about 7.15 mm of sound path) until the sub-sample step is finished.
- **2D only.** Three mics in one plane give azimuth, not elevation. The direction solver assumes a far-field source (a flat wave).
- **Servo range** is ±90° around the front, sounds behind the array are ignored by the test rig.
- **DMA runs about 3 hours** and then stops, because the transfer count is `0xFFFFFFFF` words (384000 words/s). Restart the board, or switch to an endless transfer mode for long runs.
- **Reverberant rooms and speech** produce wrong peaks more easily than claps and tones, which is what the confidence and consistency checks are for.
